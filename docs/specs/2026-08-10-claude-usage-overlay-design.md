# Claude Usage Overlay — 설계 문서

작성일: 2026-08-10

## 1. 목적

Claude 사용량을 확인하려면 Claude 앱의 설정창을 열어야 한다. 이 왕복을 없애고, 5시간 창 사용률을 항상 화면에 띄운다.

**이름 주의**: 기존 `claude-hud` 플러그인(터미널 statusline)과 별개의 프로젝트다. 패키지명은 `claude_usage_overlay`.

별개의 프로젝트지만 **저장소는 기존 `CLAUDE_HUD`를 그대로 쓴다.** 같은 목적(사용량을 눈에 보이게 하기)의 두 표시기를 한 곳에 두는 편이 낫고, 이미 이 저장소에 스펙과 플랜이 커밋돼 있다. 패키지 이름이 다르므로 섞일 일은 없다.

## 2. 왜 기존 도구로 안 되는가

`claude-hud` 플러그인은 Claude Code의 `statusLine` 설정으로 동작한다. 조사 결과 **Claude 데스크톱 앱의 Code 화면은 커스텀 statusLine을 렌더링하지 않는다.**

- 12초 동안 51회 프로세스를 샘플링했으나 `claude-hud` node 프로세스가 0회 관측됨 (`refreshInterval: 5` 설정 상태에서 2~3회는 떠야 함)
- 사용자 화면 확인 결과 입력창 아래에 HUD 없음

터미널 `claude` CLI에서는 정상 동작한다. 이 프로젝트는 앱 사용자를 위한 별도 표시기다.

## 3. 검증된 사실

모두 2026-08-10에 실측했다. 추정이 아니다.

### 3.1 사용량 조회

```
GET https://api.anthropic.com/api/oauth/usage
Authorization: Bearer <accessToken>
anthropic-beta: oauth-2025-04-20
```

응답 (1,823바이트, 왕복 330~570ms). 아래는 13:20과 13:41에 받은 본문의 **발췌**다 — 반복되는 `null` 필드와 `spend` 내부는 `...`로 줄였다. 줄이지 않은 부분은 실물 그대로이고, 특히 `limits[]`는 필드를 하나도 빼지 않았다.

(13:20 기록에는 `limits[]`의 `group`과 `scope.surface`가 빠져 있었다. 13:41 재측정에서 발견해 채웠다. 같은 날 21분 사이에 기록과 실물이 어긋났다는 사실 자체가 아래 첫 번째 교훈의 근거다.)

여기서 읽어낼 것은 넷이다.

- **문서화되지 않은 코드네임 필드가 섞여 있고 예고 없이 늘어난다.** `tangelo`, `iguana_necktie`, `omelette_promotional`, `nimbus_quill`… 이 목록을 스키마로 굳히면 안 된다. 파서는 필요한 필드만 보고 나머지는 존재 여부조차 확인하지 않는다.
- **모델별 사용량은 존재한다.** `limits[]`의 `weekly_scoped` 항목이 모델 `Fable` 6%를 담고 있다. 초기 조사에서 "모델별은 전부 null"로 본 것은 최상위 `seven_day_opus` 계열만 확인한 결과였고, 사실이 아니다.
- **`resets_at`은 `null`일 수 있다.** `nimbus_quill`에서 실제로 null이며 `utilization` 0.0과 짝을 이룬다. `five_hour`도 사용량 0인 새 창에서 null일 수 있다고 보고 설계한다.
- **창이 객체째 `null`일 수 있다.** 값이 없는 창은 두 형태로 온다 — `nimbus_quill`처럼 객체가 있고 `utilization: 0.0`인 것, `tangelo`·`cinder_cove`처럼 **통째로 `null`인 것**. `five_hour`에도 뒤의 형태가 나타날 수 있다고 보고, 그때는 0%로 읽는다. 형식이 바뀐 게 아니라 쓴 게 없다는 뜻이기 때문이다. 근거는 §5의 `usage_client`에 적었다.

시각 포맷은 마이크로초 + `+00:00` 오프셋이다. `Z` 접미사가 아니다. Python 3.12 `datetime.fromisoformat`은 양쪽 다 처리하므로 파싱 자체는 문제가 없지만, 스냅샷은 tz-aware로 다룬다.

- **쿼터를 소비하지 않는다.** 추론 호출이 아니다. 5회 연속 호출 동안 `utilization`이 변하지 않음을 확인했다.

### 3.2 엔드포인트 자체의 호출 한도 (중요)

짧은 시간에 약 8회 호출하자 차단됐다.

```
429 rate_limit_error
retry-after: 287
```

**정확한 한도는 측정하지 않았다.** "8회쯤에서 걸리고 벌칙은 약 5분"만 안다. 이 미측정 상태를 전제로 보수적인 주기를 고른다.

### 3.3 토큰 갱신

**실측해 두었지만 이 도구는 호출하지 않는다.** 이유는 §9에 있다. 나중에 필요해질 때를 위해 기록만 남긴다.

```
POST https://console.anthropic.com/v1/oauth/token
Content-Type: application/json

{ "grant_type": "refresh_token",
  "refresh_token": "<refreshToken>",
  "client_id": "9d1c250a-e61b-44d9-88ed-5944d1962f5e" }
```

응답: `access_token`, `refresh_token`, `expires_in`, `refresh_token_expires_in`, `scope`, `token_uuid`, `organization`, `account`

| 항목 | 값 |
|---|---|
| accessToken 수명 | 28,800초 (8시간) |
| refreshToken 수명 | 2,585,692초 (약 30일) |
| **refreshToken 회전** | **매 갱신마다 새 값으로 교체됨** |

자격증명 파일: `%USERPROFILE%\.claude\.credentials.json`, 최상위 키 `claudeAiOauth`
필드: `accessToken`, `refreshToken`, `expiresAt`(ms), `refreshTokenExpiresAt`(ms), `scopes`, `subscriptionType`, `rateLimitTier`

## 4. 결정 사항

| 항목 | 결정 |
|---|---|
| 스택 | Python 3.12 + tkinter 8.6 + pystray + pillow |
| 오버레이 형태 | 링 게이지 + 텍스트 2줄 |
| 오버레이 내용 | 5시간 사용률 · 리셋 카운트다운 · 마지막 갱신 시각 |
| 창 속성 | 무테두리 · 반투명(alpha 0.82) · 항상 위 · 드래그 이동 |
| 경고 임계값 | 70% 주의(노랑) / 90% 위험(빨강) |
| 트레이 아이콘 | 숫자 + 아래에서 차오르는 배경. **숫자는 항상 흰색** (§4.1) |
| 트레이 메뉴 | 오버레이 숨기기/보이기 · 지금 갱신 · 시작할 때 자동 실행 · 설정 파일 열기 · 종료 |
| 자동 실행 | 레지스트리 `HKCU\...\CurrentVersion\Run`에 등록/해제 (§9.2) |
| 폴링 주기 | 300초 (5분). 설정으로 바꿀 수 있되 하한 120초 |
| 자격증명 | **읽기 전용.** 토큰을 갱신하지 않고 파일도 쓰지 않는다 (§9) |

7일 창은 오버레이에서 제외하고 트레이 툴팁에만 넣는다. 툴팁 내용은 5시간 사용률 · 리셋 카운트다운 · 7일 사용률 · 갱신 시각이다.

**트레이 메뉴가 이 프로그램의 유일한 조작 수단이다.** 오버레이는 무테두리·항상 위 창이라 제목 표시줄도 닫기 단추도 없다. 종료 항목이 없으면 사용자가 작업 관리자로 죽여야 한다.

폴링 주기에 하한을 두는 이유는 §3.2다. 엔드포인트 한도를 모르는 상태에서 사용자가 30초를 넣으면 429 벌칙이 상시화된다.

**단 하한 120초 자체도 측정값이 아니다.** §3.2가 아는 것은 "짧은 시간에 약 8회에서 걸린다"뿐이고 그 '짧은 시간'의 길이를 모르므로, 120초(시간당 30회)가 안전하다는 보장은 없다. 기본값 300초는 보수적으로 고른 값이고 하한 120초는 그보다 약한 근거 위에 있다. §12에 미해결로 남긴다.

### 4.1 트레이 아이콘의 숫자는 흰색 하나다

처음에는 수위 경계에서 숫자 색을 뒤집기로 했다. 채운 영역 위에서는 어두운 글자, 빈 영역 위에서는 밝은 글자를 써서 각 구간의 대비를 최대로 가져가는 방식이다. **구현해서 16px로 띄워 보니 이 방식이 오히려 읽기 어려웠다.**

숫자 높이가 10px인데 수위선이 그 한가운데를 지나면 한 글자가 위아래로 쪼개진다. 그러면 밝은 절반만 글자로 보이고 나머지는 배경에 묻혀서, `62`가 `6`과 `2`의 윗동강처럼 읽힌다. 사용률이 40~70% 구간일 때 계속 이 상태가 된다.

그래서 색을 나누는 대신 **채움색을 어둡게 골라 흰 글자 하나로 통일했다.** 오버레이 링과 다른 색표를 쓰는 이유가 이것이다.

| | 배경 | 글자 | 그래서 필요한 것 |
|---|---|---|---|
| 오버레이 링 | 어두운 창 | — | 선이 **밝아야** 보인다 |
| 아이콘 채움 | — | 흰 숫자 | 배경이 **어두워야** 숫자가 보인다 |

채움색은 채도를 94% 이상 유지한 채 명도만 낮춰 골랐다. 채도를 깎으면 색만 탁해지고 대비는 거의 오르지 않는다 — 실측으로 주황의 채도를 95%에서 20%까지 낮춰도 흰 글자 대비는 2.7에서 3.9까지밖에 오르지 않았고, 같은 색을 명도만 낮추자 7.7까지 올라갔다.

| | 초록 | 주황 | 빨강 |
|---|---|---|---|
| 채움색 | `#059669` | `#d97706` | `#dc2626` |
| 흰 글자 대비 | 3.2 | 2.7 | 4.1 |

**이 값들은 일반 권장선인 4.5에 못 미친다.** 색감을 우선해 고른 결과이고, 더 어둡게 하면(대비 4.5~5.0) 읽기는 나아지지만 색이 눈에 덜 띈다. 어느 쪽을 택할지는 취향의 문제라 사용자가 화면에서 직접 비교해 고른 값을 그대로 쓴다. 나중에 바꿀 일이 생기면 `theme.FILL_*` 세 상수만 고치면 되고, 테스트가 대비 하한 2.5를 지킨다.

## 5. 모듈 구조

각 모듈은 하나의 책임만 갖고, 아래 모듈에만 의존한다.

아래는 **설계상 의미가 있는 경계**만 적은 것이다. 구현 플랜은 이걸 더 잘게 쪼갠다 — 도메인 타입(`models`), urllib 어댑터(`http_client`), 순수 함수(`theme`·`formatting`·`icon_render`), PC마다 다른 값(`winmetrics`). 그 분리는 UI와 네트워크 없이 테스트하기 위한 것이고 설계 결정을 바꾸지 않는다.

### `credentials.py`

공개 인터페이스는 `get_access_token() -> str` 하나다. 호출자는 토큰이 유효하다는 사실만 알면 되고 파일 위치도 만료 규칙도 모른다.

내부 동작은 **파일 읽기가 전부다.** 쓰지 않는다.

- 호출할 때마다 파일을 다시 읽는다. 캐시하지 않는다 — 다른 프로세스가 언제든 갱신하기 때문이다
- accessToken이 만료됐으면 `ReloginRequired("Claude Code를 한 번 실행하세요")`
- refreshToken까지 만료됐거나 파일이 없거나 깨졌으면 `ReloginRequired("claude auth login")`

두 경우 모두 같은 예외를 쓰고 문구로 구분한다. UI가 두 상태를 다르게 다룰 이유가 없고, 사용자가 할 일만 다르다.

**문구는 이 둘로 고정하고 원본 예외 텍스트를 붙이지 않는다.** 이 문자열은 그대로 `HudState.detail`이 되어 오버레이 둘째 줄과 트레이 툴팁으로 간다. 오버레이의 텍스트 예산은 164px인데 예외를 붙이면 183~614px이 되어 잘리고(`create_text`는 경고 없이 자른다), 트레이는 더 나쁘다 — Win32 `szTip`이 128 wchar 고정 버퍼라 129자에서 `ValueError`가 나고 그게 메인 스레드의 갱신 루프를 멈춘다. 진단에 필요한 원인은 `__cause__`에 남긴다.

### `usage_client.py`

`fetch_usage(token) -> UsageSnapshot`. HTTP와 도메인의 경계다.

`UsageSnapshot(five_hour_pct: float, resets_at: datetime | None, seven_day_pct: float | None, fetched_at: datetime)`

예외: `RateLimited(retry_after: int)` / `Unauthorized` / `SchemaChanged`

**`SchemaChanged` 판정 규칙 — 이것만이다.**

| | |
|---|---|
| 필수 | `five_hour` **키가 있다** |
| 0%로 읽음 | `five_hour`가 **객체째 `null`** — 값이 사라진 게 아니라 쓴 게 없다는 뜻이다 |
| 위반 | `five_hour`가 객체인데 `utilization`을 숫자로 못 읽는다 |
| 선택 | `five_hour.resets_at` · `seven_day.utilization` — 없거나 `null`이거나 못 읽으면 `None` |
| 무시 | **그 외 모든 키.** 모르는 키가 나타나는 것은 위반이 아니다 |

규칙을 이렇게 좁히는 이유는 §3.1이다. 응답에는 코드네임 필드가 계속 추가되므로 "예상과 다른 것이 있으면 위반"으로 만들면 첫 실행부터 오탐한다.

`five_hour`가 통째로 `null`인 것을 0%로 읽는 이유도 같은 절이다. `tangelo`·`cinder_cove`가 그 형태로 오는 것을 실측했으므로, 5시간 창이 완전히 빈 시점에 같은 형태가 올 수 있다. 이때 `SCHEMA_ERROR`를 띄우면 **가장 평화로운 순간(사용량 0)에 경고가 뜬다.** 0%를 초록으로 그리는 쪽이 틀렸을 때의 대가도 작다 — 실제로 형식이 바뀐 것이었다면 다음 응답에서 `utilization`이 안 읽혀 곧바로 잡힌다.

반대로 `five_hour`가 객체로 오는데 그 안의 `utilization`이 숫자가 아니면 그건 진짜로 보여줄 숫자가 사라진 것이므로 위반이다. `five_hour` 키 자체가 없어도 위반이다. 이 구분은 실측 근거가 없는 추정이므로 §12에 남긴다.

`resets_at`을 못 읽는 것은 위반이 아니다. 사용률은 멀쩡한데 카운트다운만 못 그리는 상황이고, 그때는 카운트다운 자리를 비운다. 숫자를 지어내지 않는다는 원칙은 지키면서 멀쩡한 숫자를 버리지 않는다.

### `poller.py`

백그라운드 스레드에서 300초마다 조회한다. 마지막 성공 스냅샷과 연속 실패 시간을 들고 있으면서 상태를 **하나의 값**으로 계산한다. UI는 이 상태만 보면 된다.

```
Status = OK | STALE | RATE_LIMITED | RELOGIN | SCHEMA_ERROR
```

`RELOGIN`의 문구는 `credentials`가 정하고 poller는 그대로 넘긴다. "Claude Code를 한 번 실행하세요"와 "claude auth login"을 가르는 것은 자격증명 파일의 상태이고, 그건 poller가 아는 일이 아니다.

401은 3회 연속일 때만 `RELOGIN`으로 넘긴다. 이유는 §8에 있다.

### `overlay.py`

tkinter 창. Canvas 호(arc)로 링을 그린다.

**1초마다 틱을 돌지만 네트워크는 건드리지 않는다.** 카운트다운은 `resets_at`에서 로컬 계산한다. 화면은 매초 살아 움직이고 API는 5분에 한 번만 부른다.

`resets_at`이 `None`이면 카운트다운 자리에 `—`를 넣는다. 링과 숫자는 정상으로 그린다.

### `tray.py`

pystray 아이콘과 메뉴. pillow로 이미지를 그린다.

**아이콘 크기를 상수로 박지 않는다.** 배율 100%에서 16px, 150%에서 24px이므로 런타임에 `GetSystemMetrics(SM_CXSMICON)`로 조회하고 어떤 크기로도 그린다.

메뉴는 §4의 다섯 항목이고, 그중 `종료`가 이 프로그램을 끄는 유일한 방법이다. 툴팁은 `HudState` 하나만 보고 만든다.

### `autostart.py`

`HKCU\Software\Microsoft\Windows\CurrentVersion\Run`의 `ClaudeUsageOverlay` 값을 읽고·쓰고·지운다. 인터페이스는 `is_enabled()` / `enable()` / `disable()` 셋이고, 트레이 메뉴의 체크 항목이 이것만 호출한다.

근거는 §9.2다.

### `config.py`

`%APPDATA%\claude-usage-overlay\config.json` — 창 위치, 임계값, 폴링 주기, 오버레이 표시 여부.

파일이 없거나 깨져 있으면 **예외를 던지지 않고 기본값을 쓴다.** 설정 하나 때문에 HUD 전체가 안 뜨면 안 된다.

## 6. 데이터 흐름

```
  .credentials.json ──(읽기 전용)──→ credentials
                                          │
[poller 스레드]  300초마다 토큰 재읽기 + 조회
       ↓
  HudState (잠금으로 보호된 최신 값 하나)
       ↓ 1초마다 읽어 감
[메인 스레드]  overlay + tray
       ↑
[트레이 스레드]  메뉴 조작 → after()로 메인 스레드에 넘김
```

화살표가 파일 쪽으로 되돌아가지 않는다는 것이 이 그림의 요점이다. 이 도구는 `.credentials.json`에 쓰지 않는다.

**poller는 스트림이 아니라 최신 상태 하나만 노출한다.** 큐를 쓰지 않는 이유는 UI가 과거 값을 소비할 이유가 없어서다 — 5분 동안 쌓인 스냅샷을 순서대로 그릴 일이 없고, 큐가 비었을 때 무엇을 그릴지 UI가 또 판단해야 한다. `HudState` 하나를 잠금으로 감싸고 메인 스레드가 1초마다 읽어 가면 그 판단이 사라진다.

tkinter **창 조작**은 메인 스레드에서만 한다. 트레이 메뉴 콜백은 pystray 스레드에서 도는데, 거기서 창을 직접 건드리는 대신 `after()`로 메인 스레드에 넘긴다. 이 경계를 지키면 네트워크 대기 중에 UI가 멈추지 않는다.

## 7. 상태별 표시

§5의 `Status` 다섯 값이 모두 화면에 대응된다. `OK`만 사용률에 따라 넷으로 갈린다. 정의되지 않은 상태가 없어야 구현자가 색을 임의로 고르지 않는다.

| Status | 사용률 | 오버레이 | 트레이 아이콘 |
|---|---|---|---|
| `OK` | ~69% | 초록 링 + 숫자 | 초록 채움 + 숫자 |
| `OK` | 70~89% | 노랑 링 | 노랑 채움 + 숫자 |
| `OK` | 90~99% | 빨강 링 | 빨강 채움 + 숫자 |
| `OK` | 100% | 빨강 꽉 참 | 빨강 꽉 참 + **✕** |
| `STALE` | 없음 (첫 조회 전) | 링 비움 + "불러오는 중" | 회색 + **…** |
| `STALE` | 마지막 값 | 링 흐림 + "N분째 갱신 실패" | 아이콘 흐림 |
| `RATE_LIMITED` | 마지막 값 | 링 흐림 + "호출 한도 — 잠시 후 재시도" | 아이콘 흐림 |
| `SCHEMA_ERROR` | 없음 | 링 비움 + "데이터 형식이 바뀜" | 회색 + **?** |
| `RELOGIN` | 없음 | 링 비움 + 안내 문구 | 회색 + **!** |

색이 먼저 말하고 기호는 나중이다. 배경색 셋으로 갈린다.

- **초록·노랑·빨강** — 값이 있고 최신이다
- **흐림** — 값이 있지만 낡았다 (`STALE`, `RATE_LIMITED`)
- **회색** — 값이 없다 (`SCHEMA_ERROR`, `RELOGIN`, 첫 조회 전). 이 안에서만 `?`·`!`·`…`가 구분 부담을 진다

**`STALE`이 표에 두 번 나오는 이유**는 마지막 스냅샷이 있느냐로 갈리기 때문이다. 폴러의 초기 상태는 `(STALE, snapshot=None)`이고, 이걸 `SCHEMA_ERROR`와 같은 `?`로 그리면 **프로그램을 켤 때마다 몇 초 동안 "데이터 형식이 바뀜" 기호가 뜬다.** 기호가 상태를 가리키는 이상 이 자리를 비워둘 수 없다.

`RATE_LIMITED`를 `STALE`과 같은 흐림으로 둔 이유는 사용자가 할 일이 같기 때문이다 — 둘 다 기다리면 낫는다. 문구만 다르다.

`RELOGIN`의 안내 문구는 두 가지다.

| 원인 | 문구 |
|---|---|
| accessToken만 만료 | "토큰 만료 / Claude Code를 한 번 실행하세요" |
| refreshToken 만료 · 파일 없음 · 파일 손상 | "재로그인 필요 / claude auth login" |

**100%는 숫자를 넣지 않는다.** 16px 폭에 세 자리 굵은 숫자는 물리적으로 들어가지 않는다. ✕로 대체한다.

## 8. 실패 처리

| 상황 | 동작 |
|---|---|
| 네트워크 실패 | 마지막 값 유지, 흐리게, "N분째 갱신 실패" |
| 429 | `retry-after` 헤더를 그대로 존중하고 그때까지 호출하지 않음 |
| 401 | 다음 틱에 파일을 다시 읽어 재시도. **백오프를 태우지 않는다.** 3회 연속이면 `RELOGIN` |
| accessToken 만료 | `RELOGIN` + "Claude Code를 한 번 실행하세요". 우리가 갱신하지 않는다 |
| refreshToken 만료 · 파일 없음 · 손상 | `RELOGIN` + "claude auth login" |
| `resets_at`이 없음 | 카운트다운만 `—`. 사용률은 정상 표시 |
| 스키마 변경 | "데이터 형식이 바뀜" 표시. **숫자를 지어내지 않는다** |

401에 즉시 `RELOGIN`을 띄우지 않는 이유는, 만료 직전 토큰으로 호출한 순간 Claude Code가 파일을 갱신하는 정상 경합이 있기 때문이다. 다음 틱에 파일을 다시 읽으면 저절로 낫는다. 세 번을 넘기면 그건 경합이 아니라 인증 문제다.

폴링 실패 시 지수 백오프(300 → 600 → 1200초, 최대 1800초).

**401은 이 백오프의 예외다.** 백오프를 태우면 "다음 틱"이 5분에서 10분, 20분으로 늘어나 3회를 채우는 데 35분이 걸린다. 5분이면 나을 경합을 위해 만든 유예가 오히려 회복을 늦춘다. 401 재시도는 기본 주기를 그대로 쓰고, 네트워크 실패 카운터도 건드리지 않는다 — 인증 경합과 네트워크 단절은 다른 사건이므로 한 카운터를 공유하면 안 된다.

## 9. 자격증명은 읽기만 한다

갱신 API는 §3.3에 실측해 두었지만 **이 도구는 호출하지 않는다.** `.credentials.json`은 읽기 전용이다.

이유는 refreshToken이 매 갱신마다 회전하기 때문이고, 위험은 양쪽으로 흐른다.

- 우리가 새 refreshToken을 저장하지 못하면 → **우리가** 죽는다
- 우리가 회전시키면, 옛 refreshToken을 메모리에 들고 있는 Claude Code와 데스크톱 앱이 다음 갱신 때 → **본체가** 죽는다

두 번째가 훨씬 아프다. 사용량을 5분 빨리 보려다 사용자의 Claude 인증을 깨뜨리는 것은 어떤 편의로도 상쇄되지 않는다. 파일을 쓰지 않으면 두 위험이 동시에 사라진다. 원자적 쓰기도, 외부 갱신 감지도, 회전 실패 복구도 필요 없어진다 — 없는 기능은 깨지지 않는다.

### 대가

accessToken 수명은 8시간이고 그 갱신은 Claude Code가 자기 필요에 따라 한다. 우리는 편승할 뿐이다. 따라서 **Claude Code를 8시간 넘게 쓰지 않으면 우리 토큰도 만료되고 조회가 멈춘다.**

그때 숫자를 지어내지 않고 "Claude Code를 한 번 실행하세요"를 표시한다. 5시간 창은 Claude를 쓰지 않는 동안 어차피 움직이지 않으므로, 이 구간에서 잃는 정보는 크지 않다.

이 대가가 실제로 발생하는지는 아직 모른다. Claude Code가 파일을 저절로 갱신하는지 확인하지 못했다 — 확인 방법은 §12에 적었다.

### 갱신을 넣어야 한다면

관찰 결과 파일이 저절로 갱신되지 않는다면 그때 §3.3의 요청을 구현한다. 함께 넣을 방어는 셋이다.

1. **원자적 쓰기** — 임시 파일에 쓰고 `os.replace`
2. **갱신 직전 재읽기** — 이미 갱신돼 있으면 우리는 갱신하지 않는다
3. **만료 30분 전에만** — 회전 횟수를 줄이는 것이 사고 확률을 줄인다

순서를 이렇게 잡은 이유는 되돌리기 비용이 비대칭이라서다. 갱신 로직을 나중에 넣는 것은 순수한 추가지만, 잘못된 회전으로 깨진 인증은 재로그인 없이 되돌릴 수 없다.

**도구와 Claude Code를 모두 30일 넘게 쓰지 않으면 재로그인이 필요하다.** 읽기 전용이든 아니든 이건 피할 수 없다. 조용히 실패하는 대신 명확히 표시한다 — 이번 조사에서 인증이 죽어 있던 것을 우연히 발견한 것과 같은 상황을 만들지 않는다.

### 9.2 레지스트리에는 왜 써도 되는가

앞 절이 "사용자 시스템에 쓰지 않는다"를 길게 논증했으므로, 자동 실행 등록(§4)이 그 원칙을 어기는 것처럼 보인다. 어기지 않는다. 두 쓰기의 성질이 다르다.

| | `.credentials.json` | `Run` 키의 `ClaudeUsageOverlay` 값 |
|---|---|---|
| 소유자 | Claude Code와 데스크톱 앱이 공유 | **우리만 읽고 쓴다** |
| 다른 프로그램이 읽는가 | 읽는다. 그래서 우리 쓰기가 남을 깨뜨린다 | 아무도 안 읽는다 |
| 값이 회전하는가 | refreshToken이 매 갱신마다 바뀐다 | 고정 문자열이다 |
| 최악의 결과 | **사용자의 Claude 인증이 깨진다** | 자동 실행이 안 되거나, 지워진 경로를 가리키는 항목이 남는다 |
| 되돌리기 | 재로그인해야 한다 | 메뉴에서 체크 해제, 또는 작업 관리자 시작 프로그램 탭 |

§9가 막으려던 것은 "쓰기" 자체가 아니라 **남이 의존하는 공유 상태를 우리가 회전시키는 것**이다. `Run` 키에는 그 성질이 없다.

지키는 선은 둘이다. `HKCU`만 건드려 관리자 권한을 요구하지 않고, `ClaudeUsageOverlay`라는 우리 값 이름 하나만 다룬다 — 키를 열거하거나 남의 값을 건드리지 않는다.

## 10. 테스트

HTTP를 목으로 두고 단위 테스트한다. 아래 셋이 로직의 전부다.

- `credentials` — 만료 판정, 두 가지 만료의 문구 구분, 파일 없음·손상, **파일을 쓰지 않는다는 것**
- `usage_client` — §3.1 실제 응답 파싱, `resets_at` null, 모르는 키 무시, 429(retry-after 추출), 401
- `poller` — 백오프 계산, 상태 전이, 401 3회 연속 후 `RELOGIN`

`credentials`의 "파일을 쓰지 않는다"는 단언은 §9 전체를 지키는 테스트다. 호출 전후 파일 내용이 바이트 단위로 같은지 본다.

UI는 수동 확인한다.

## 11. 범위에서 제외

7일 창 상시 표시(툴팁에만) · 히스토리 그래프 · 알림 팝업 · 다중 계정 · macOS/Linux 지원 · 토큰 갱신(§9).

**모델별 사용량**도 제외한다. 단 이유가 바뀌었다 — §3.1에서 확인했듯 `limits[]`에 값은 실재한다. 못 하는 게 아니라 안 하는 것이다. 5시간 창 하나를 한눈에 보자는 것이 §1의 목적이고, 모델별 항목을 얹으면 오버레이가 대시보드가 된다. 나중에 마음이 바뀌면 `limits[]`에서 `kind == "weekly_scoped"`를 골라내는 파싱만 추가하면 된다.

## 12. 미해결 사항

- **`.credentials.json`이 저절로 갱신되는가** — 가장 중요하다. §9의 읽기 전용 결정이 여기에 달려 있다. 2026-08-10 13:21 기준 파일 mtime은 `12:22:39`, `expiresAt`는 `20:22:39`로 정확히 8시간 차이였다. 즉 12:22에 누군가 갱신했지만 **그게 Claude Code의 자동 갱신인지 §3.3의 수동 테스트인지 구분되지 않는다.** 확인 방법은 파일 mtime을 며칠 지켜보는 것이다 — Claude Code를 평소처럼 쓰면서 mtime이 8시간 주기로 저절로 움직이면 읽기 전용으로 충분하고, 움직이지 않으면 §9의 "갱신을 넣어야 한다면"으로 간다.
- **엔드포인트 호출 한도의 정확한 값** — 5분 주기는 안전하다고 판단해 고른 값이지 측정값이 아니다. 구현 후 장시간 돌려 429가 나오는지 확인한다. **하한 120초는 근거가 더 약하다**(§4). 기본값으로 429가 안 나는 것을 확인한 뒤, 하한을 검증할지 아니면 그냥 300초로 올릴지 정한다.
- **`five_hour`가 객체째 `null`로 오는 형태를 실제로 본 적이 없다** — §3.1에서 그 형태를 관측한 것은 `tangelo`·`cinder_cove` 같은 다른 창이고, 5시간 창에서 재현하려면 사용량 0인 창을 기다려야 한다. §5의 "0%로 읽는다"는 그 유추 위에 서 있다. 5시간 창이 비는 시점에 로그로 확인한다.
- **`client_id`의 안정성** — 갱신을 하지 않으므로 **지금은 무관하다.** 위 관찰 결과 갱신 로직을 넣게 되면 그때 다시 본다. 공개된 Claude Code OAuth client id는 변경되면 갱신이 깨지므로, 넣을 때는 400/401 응답에 상태 코드를 남겨 진단 가능하게 한다.
- **엔드포인트의 비공개성** — `/api/oauth/usage`는 문서화된 공개 API가 아니다. §3.1에서 본 코드네임 필드들이 그 증거다. 예고 없이 바뀔 수 있어 `SchemaChanged`를 별도 상태로 두고, 형식이 바뀌면 잘못된 숫자를 보여주는 대신 바뀌었다고 말한다.
